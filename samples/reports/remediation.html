1Management plane isolation  · Task 1 of 13HIGH
What to do: Only LAN may manage this firewall. Right now 1 rules let other zones (VPN, WAN, VLANs) reach the admin interface or SSH. Fix them in the order below:
Do these in order. Most of these rules are auto-created by SonicWall, so a few settings changes clear almost all of them — you do NOT delete 30+ rules by hand.

Step 1: Delete (or set Action = Deny) these 1 remaining rule(s) by hand.
  Go to POLICY > Rules and Policies > Access Rules, find each one by its zone pair + service, and delete it:
    - GUEST -> LAN  |  service: HTTPS Management  |  source: Any  |  destination: All X0 Management IP
Why: The firewall's own management plane must be isolated. Any VPN user or device on a segmented VLAN that can reach the admin GUI or SSH can attack the firewall itself — a single compromised VPN session or VLAN host would defeat all segmentation. Only the LAN zone may manage the device.
Standard: NIST SP 800-53 AC-6 (Least Privilege) & SC-7 (Boundary Protection); CIS Control 12.6 (dedicated/secure admin access); PCI DSS v4.0 Req 1.3 & 2.2.7; FFIEC Information Security.
2Management (incl. SSH) source restriction  · Task 2 of 13HIGH
What to do: Restrict LAN admin + SSH access to the jumpbox only (the host running the Connect Secure agent). Currently these 2 rules allow 'Any' source:
Step 1: Create the admin source object (once).
  1. OBJECT > Match Objects > Addresses > Add.
  2. Name: Mgmt-Jumpbox   Zone: LAN   Type: Host.
  3. IP address: the jumpbox IP — the jumpbox that runs the Connect Secure agent. Save.
     (If there are two admin hosts, make an Address GROUP named Mgmt-Jumpbox containing both — max 2.)

Step 2: Open each of these 2 LAN admin/SSH rules (POLICY > Rules and Policies > Access Rules) and change ONLY the Source field to Mgmt-Jumpbox, so only the Connect Secure agent on the jumpbox can reach the firewall. Each rule and its exact change is listed below:

  RULE: LAN -> LAN  |  HTTPS Management  |  destination: All X0 Management IP   [auto-created]
     >>> CHANGE Source:  Any  =>  Mgmt-Jumpbox

  RULE: LAN -> LAN  |  SSH Management  |  destination: All X0 Management IP   [auto-created]
     >>> CHANGE Source:  Any  =>  Mgmt-Jumpbox

(These are auto-added management rules, but here you EDIT their Source field rather than delete them — keep management enabled on LAN, just lock the source to the jumpbox. The restriction persists.)
Why: An 'Any' source exposes the firewall admin interface and SSH to every host in that zone. Restricting the source to the jumpbox address object means only the Connect Secure agent can manage the firewall. SSH in particular must be limited to at most 2 admin IPs.
Standard: PCI DSS v4.0 Req 1.3 & 2.2.7; NIST SP 800-53 AC-6 (Least Privilege) & SC-7; CIS Control 12.
3VPN user isolation (user-to-user)  · Task 3 of 13HIGH
What to do: Block VPN-user-to-VPN-user traffic — turn OFF intra-zone communication on the SSLVPN zone(s):
OBJECT > Zones > edit the SSLVPN zone > set 'Allow Interface Trust' / intra-zone communication to OFF (deny).
Why: Every remote VPN user lands in this zone. With intra-zone communication on, one compromised remote session can scan and attack every other remote user directly. Turning it off confines each session to its own path to the servers it needs.
Standard: NIST SP 800-53 SC-7 (Boundary Protection) & AC-4 (Information Flow Enforcement); CIS Control 12; PCI DSS v4.0 Req 1.3.
4LAN-to-VPN-user isolation  · Task 4 of 13HIGH
What to do: Remove (or set to DENY) these 1 rules that let the LAN initiate connections TO VPN users (SSLVPN):
LAN -> SSLVPN  |  service: Any  |  source: Any  |  destination: Any
Why: Remote VPN users reaching LAN servers is expected and stays allowed. But the LAN initiating connections back TO remote user devices is not needed and only gives an attacker on the LAN a path to remote endpoints. Keep SSLVPN->LAN; block LAN->SSLVPN.
Standard: NIST SP 800-53 SC-7 & AC-4 (Information Flow); CIS Control 12; PCI DSS v4.0 Req 1.3.

6Branch-to-branch VPN (WAN -> LAN)  · Task 6 of 13HIGH
What to do: Pin these 1 WAN -> LAN rules to the known branch subnets — source = other branches' LANs, destination = this branch's LAN (10.20.10.0/24). They must never be 'Any':
These rules carry branch-to-branch VPN traffic but currently accept ANY source to ANY/WAN-IP destination. We know every branch's LAN subnet from their configs, so pin BOTH ends:
  source      = the OTHER branches' LANs
  destination = THIS branch's LAN (10.20.10.0/24)

Step 1: Create a Network object for each OTHER branch's LAN (OBJECT > Match Objects > Addresses > Add; Type: Network):
    - Name: Branch-Westside-LAN   Network: 10.30.10.0   Mask: 255.255.255.0   (= 10.30.10.0/24)
    - Name: HQ-Main-LAN   Network: 10.10.10.0   Mask: 255.255.255.0   (= 10.10.10.0/24)

Step 2: Create an Address GROUP named 'Branch-Trusted-Nets' and add every Step 1 object. (This is the SOURCE for all the rules below.)

Step 3: Edit each rule below — set BOTH its Source and Destination. This branch's LAN is the built-in 'LAN Primary Subnet' object (= 10.20.10.0/24):
  RULE: WAN -> LAN | service: RDP
     >>> Source:       Any  =>  Branch-Trusted-Nets
     >>> Destination:  WAN Interface IP  =>  LAN Primary Subnet   (= 10.20.10.0/24)
Why: A WAN -> LAN rule with an 'Any' source (and 'Any'/WAN-IP destination) lets the entire Internet into the trusted LAN, not just the sister branches. Because every branch's LAN subnet is known from its config, both ends can be pinned exactly: only the sister branches' LANs reach only this branch's LAN.
Standard: PCI DSS v4.0 Req 1.2/1.3 (restrict inbound to that required); NIST SP 800-53 SC-7 (Boundary Protection); CIS Control 12.
7Port forwards  · Task 7 of 13HIGH
What to do: Restrict these 1 port forward(s) — each publishes an internal host to the entire Internet. Edit the WAN access rule and change ONLY its Source from Any to the known source IPs:
FORWARD: TCP 3389 on 203.0.113.18 (X1 inbound)  =>  10.20.30.41   [NAT policy: RDP to teller PC]
  RULE: WAN -> LAN  |  service: RDP  |  source: Any  |  destination: WAN Interface IP
     >>> CHANGE Source:  Any  =>  an address object/group holding only the partner or vendor IPs that need this service

If nobody outside needs the service any more, remove the NAT policy (POLICY > Rules and Policies > NAT Rules) and its WAN access rule instead.
Why: A port forward open to any source hands the internal server straight to Internet-wide scanning and exploitation — the firewall passes the traffic through to it. Limiting the source to the partner/vendor IPs that need the service removes the broad exposure without breaking the integration.
Standard: PCI DSS v4.0 Req 1.3 & 1.4; NIST SP 800-53 SC-7 (Boundary Protection); CIS Control 12.
8VPN MFA  · Task 8 of 13HIGH
What to do: SSL VPN is enabled but has NO multi-factor authentication. Choose ONE option:
OPTION A  --  ADD MFA   (preferred)
  Require a second factor for every SSL VPN login using DUO,
  Entra ID, or the firewall's built-in one-time passwords:
    - TOTP:  DEVICE > Users > Local Users & Groups > edit the
             SSL VPN user group > One-time passwords: TOTP
             (users enrol an authenticator app at next login).
    - DUO:   set up the DUO Authentication Proxy as a RADIUS
             server, then point SSL VPN auth at it
             (DEVICE > Users > Settings > Authentication, add the
             RADIUS server; assign it to the SSL VPN user domain).
    - Entra: configure SAML/SSO to Entra ID and apply it to the
             SSL VPN portal (DEVICE > Users > Settings > SSO/SAML).

OPTION B  --  DISABLE SSL VPN   (if MFA will NOT be added)
  Turn SSL VPN off until MFA is in place:
    - NETWORK > SSL VPN > Server Settings > uncheck the WAN (and
      any other) zone under 'SSL VPN Server', and disable the
      SSL VPN user portal.

(Confirm the exact menu path for your SonicOS build.)
Why: SSL VPN grants remote access to the internal network. Password-only remote access is a leading breach cause; MFA stops stolen credentials from turning into remote network access. If MFA cannot be added, the safer posture is to turn SSL VPN off rather than run remote access on single-factor passwords.
Standard: FFIEC Authentication guidance (2021); PCI DSS v4.0 Req 8.4.2 & 8.5 (MFA for remote access); NIST SP 800-53 IA-2(1).

10VLAN segmentation  · Task 10 of 13MEDIUM
What to do: Review this firewall's VLANs against the suggested VLAN plan: 5 suggested VLAN(s) are missing and 1 configured VLAN(s) match no role.
Suggested VLANs not present on this firewall (5 of 10) — add each one the site has devices for, with the segmentation below:
  - VLAN 10  Management — Firewalls, switches, APs, mgmt interfaces
      Segmentation: Most restricted. Permit only from admin/jump box; deny from User, Guest, IoT. No inbound internet; outbound to vendor update sources only.
  - VLAN 20  Servers — On-prem physical & virtual servers
      Segmentation: Allow only required ports from User VLAN. No inbound from Guest/IoT. No direct inbound internet; publish externally via reverse proxy / DMZ.
  - VLAN 60  Wireless — Corporate — Trusted staff Wi-Fi
      Segmentation: Treat as trusted user VLAN. 802.1X or strong PSK. Same server access policy as wired users.
  - VLAN 80  IoT / BYOD — Smart devices, thermostats, BYOD (incl. HVAC, postage meters)
      Segmentation: Isolate from corporate. Internet limited to required cloud endpoints. Deny access to Servers, Mgmt, Workstations.
  - VLAN 100  DMZ — Public-facing / published services
      Segmentation: Strict firewall both directions. Deny initiation into internal VLANs; internal reaches DMZ on required ports only.

Configured VLANs that match no expected role — name them and classify (or remove if unused):
  - VLAN 150 · X0:V150 · zone LAN · 10.20.150.1/24
Why: Segmenting devices by role (management, servers, users, phones, printers, Wi-Fi, guest, IoT, CCTV, DMZ) limits lateral movement: a compromised printer, camera or guest device cannot reach servers or the management plane. Missing or unnamed VLANs mean that segmentation is either absent or impossible to verify.
Standard: PCI DSS v4.0 Req 1.3 (network segmentation); NIST SP 800-53 SC-7 (Boundary Protection) & AC-4; CIS Control 12; FFIEC Information Security.
11Ping / ICMP (WAN)  · Task 11 of 13MEDIUM
What to do: Stop the firewall answering ping from the Internet (1 WAN Ping rule(s) currently respond to any source). Keep internal (LAN) ping enabled:
DO THIS (one action): NETWORK > Interfaces > edit each WAN interface > Management tab > UNcheck 'Ping'. Apply.
  Leave 'Ping' ENABLED on the LAN interface — internal ping is fine and useful for monitoring.

Then delete (or set to DENY) any Ping rule that remains:
    - WAN -> WAN  |  service: Ping  |  source: Any  |  destination: WAN Interface IP
Why: Answering ICMP echo from the Internet lets attackers discover and confirm the firewall's public IPs during reconnaissance. Internal ping from the LAN is fine; only the Internet-facing ping response should be turned off.
Standard: NIST SP 800-53 SC-7 (Boundary Protection); CIS Control 12; attack-surface reduction / defense-in-depth.

3Missing NSM rules  · Task 3 of 10HIGH
What to do: Bring this firewall under NSM management from the RT Datacenter: enable the GMS/NSM management channel and add the RT Datacenter management rules.
Step 1: Enable NSM management on the firewall.
  1. DEVICE > Settings > Administration — GMS/NSM settings (SonicOS uses the GMS settings for NSM management).
  2. Turn ON 'Enable management using GMS/NSM' and point it at the NSM server in the RT Datacenter. Use the same management mode as the rest of the fleet (copy it from a compliant firewall).
  3. Save, then confirm the firewall shows as managed/online in the NSM console.

Step 2: Allow firewall management from the RT Datacenter.
  1. OBJECT > Match Objects > Addresses — make sure an Address Group named RT Datacenter exists holding the datacenter management addresses (copy its members from a compliant firewall).
  2. POLICY > Rules and Policies > Access Rules — add (or fix) the management rules: zone WAN (or VPN if NSM is reached through the tunnel) -> WAN, services HTTPS Management and SSH Management, Source = RT Datacenter, Destination = the firewall's management IPs.
  3. Do NOT use 'Any' as the source — only the datacenter object.
Why: The fleet is managed centrally by NSM from the RT Datacenter. A firewall outside NSM does not receive the standard policy, firmware and backup management the other firewalls get, so it drifts out of compliance and cannot be audited or fixed centrally.
Standard: Client management standard (NSM); NIST SP 800-53 CM-6 (Configuration Settings) & CM-7 (Least Functionality); CIS Control 4 (Secure Configuration).
